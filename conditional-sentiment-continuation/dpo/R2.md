# Conditional Sentiment Continuation Model R2 (DPO)

For `R2`, we'll use TRL's DPOTrainer with the `R1` SFT checkpoint as the initial policy and a frozen copy of `R1` as the reference model to apply DPO post-training.

The training objective will teach the policy to increase the relative likelihood of `chosen` continuations and decrease the relative likelihood of `rejected` continuations, while the reference model anchors the update to `R1`.

We'll also implement proper training recovery:

- Save periodic checkpoints, including optimizer and scheduler state.
- Detect existing checkpoints automatically.
- Resume from the latest checkpoint if an interrupted run is found.
- Save a separate best-validation checkpoint and a final model.
- Use tqdm to show progress and useful training metrics.

One important distinction: resuming a checkpoint is not the same as starting another training run from the best model. Resuming restores the training state (including optimizer and step count); starting a fresh run from a saved model initializes a new optimizer. We'll support both.

## Dataset

First, we will use `R1` to create four candidate continuations for each example. Next, we use `E1-1_2logits` to classify each candidate as either "positive" or "negative" with logits. Then, for this example, we will either discard it or pick one candidate as `chosen` and another candidate as `rejected` based on the selection rules introduced below. Lastly, we collect prompt, sentiment, `chosen` and `rejected` candidate continuations and create an example out of them in our dataset for training/validating `R2`.

Note: For brevity, in the following, `E1` and `E1-1_2logits` are used interchangeably.

**What we want DPO to learn from?**

We want DPO to explicitly learn to prefer a continuation that satisfies the requested sentiment over one that violates it. Therefore, we should explicitly consider both the requested sentiment and predicted sentiment (by our previously built sentiment classifier, `E1`). This directly governs how we pick `chosen` and `rejected` pairs.

Let's formalize it.

For a positive prompt:

- Chosen: the candidate with the highest positive logit among candidates predicted positive.
- Rejected: the candidate with the highest negative logit among candidates predicted negative.
 
For a negative prompt, reverse the roles.

Exceptions: if none of the candidates is classified as the requested sentiment, discard that prompt rather than create a chosen candidate that violates the instruction.

Likewise, if all candidates are classified as the requested sentiment, we can still create a useful pair by choosing the strongest candidate and rejecting the weakest one, provided their reward difference is sufficiently large.

The selection logic becomes:
```
Candidate availability              Chosen                                      Rejected
--------------------------------    ----------------------------------------    ------------------------------------------
Both predicted classes available    Strongest correctly classified candidate    Strongest incorrectly classified candidate

Only requested class available      Strongest correctly classified candidate    Weakest correctly classified candidate

Only opposite class available       Discard prompt                              Discard prompt
```

This creates a clear learning signal for DPO.

This gives us three desirable properties:

1. The chosen candidate is always classified by E1 as having the requested sentiment.
2. If a candidate from the opposite class exists, we use the strongest such candidate as the rejected example.
3. If all candidates are classified correctly, we can still create a preference pair based on the difference in confidence.

A small example
```
Suppose the requested sentiment is positive, and E1 produces these results:

Candidate	Negative probability	Positive probability	Prediction
A	        0.80	                0.20	                Negative
B	        0.65	                0.35                	Negative
C	        0.30	                0.70                	Positive
D	        0.10	                0.90                	Positive
```
Our algorithm selects:

- Chosen: D, because it has the highest positive probability.
- Rejected: A, because it is the most confidently negative candidate.

The resulting reward margin is: $$0.90-0.20=0.70$$

One subtle point: the all-correct case is still a relative preference, not a positive-versus-negative comparison. That is acceptable, but we can distinguish these two types of pairs in the diagnostic dataset if we want to analyze them separately.

A useful implementation detail: we would use softmax probabilities rather than raw logits for ranking. With two classes, the predicted class is argmax(logits), and the target-class probability tells us how confidently E1 supports the requested sentiment. It also makes the reward margin easy to interpret.

**preference dataset**

We build an offline preference dataset using the R1 SFT model as the candidate generator and our E1 sentiment classifier `E1-1_2logits` as the reward model.

This lets us isolate what DPO actually learns: given the same prompt and two possible continuations, prefer the continuation that better satisfies the requested sentiment.

Our pipeline will be:
```
            SST-2 source examples
    Reuse the same prompt transformation as R1
                      ↓
                R1 SFT model
    Generate 4 candidate continuations for each prompt
                      ↓
        E1 sentiment classifier
Score each complete review against the requested sentiment
                      ↓
                Preference pair
            Chosen              Rejected
```

A resulting dataset record will look like this:
```json
{
  "prompt": "Sentiment: positive\nContinue the following review:\nThe movie starts slowly but",
  "chosen": " eventually becomes an entertaining and memorable experience.",
  "rejected": " never manages to become interesting or enjoyable."
}
```

For each candidate, the reward classifier scores the complete natural-language review:
```math
R(x,s)=P_{\text{E1}}(\text{requested sentiment}\mid x+s)
```

Here, $x$ is the existing prefix and $s$ is the generated continuation.

One caveat: E1 is an imperfect reward model. DPO will learn preferences according to its judgments, which may not always match human judgments. That's actually useful to observe in this experiment.

**The good and the bad**

By eyeballing through some preference examples, we see at least three different phenomena.

A. Some preferences are sensible.

For example:
- Prompt: that loves its characters and communicates something
- Chosen: fresh about what makes them tick
- Rejected: of a strange, twisted sense of narrative direction

The chosen continuation receives a substantially higher positive reward. It also seems more naturally positive.

B. Some preferences are questionable.

Consider:
- Prompt: it takes a strange kind of laziness to waste the talents of robert forster, anne meara
- Chosen: or any of his ilk
- Rejected: - and marina

The chosen continuation is not necessarily a good continuation. It is simply more strongly classified as negative by E1.

C. Some continuations are semantically awkward or incomplete.

For example:
- Prompt: it's a charming
- Chosen: , and most of all
- Rejected: and utterly beautiful documentary about american culture

The chosen continuation has a higher sentiment score, but the rejected continuation may actually be more fluent and coherent.

These examples reinforce an important distinction:
```math
\text{Preference according to reward model}
\neq
\text{Human preference}
```

This is not a reason to abandon the dataset. It is an opportunity to understand what DPO learns when its preference labels come from an imperfect reward model.

To reach a high quality preference pairs dataset, we can prompt frontier LLMs to both generate candidate continuations and make reward assignment or employ human experts for this job.

There are two particularly important limitations to watch.

First, the classifier may reward sentiment without rewarding quality. For example, it may give a high positive score to a continuation containing many positive adjectives even if the text is awkward. This is a simple demonstration of reward-model limitations.

Second, selecting the highest and lowest scores from four candidates creates relative preferences, not necessarily good preferences. Even if all four candidates are poor, one will still be the winner. The reward-margin filter helps, but we should manually inspect examples too.

One further experiment worth doing is comparing the reward classifier's prediction against the requested sentiment for both chosen and rejected continuations. That tells us whether DPO is learning from meaningful preference differences or merely from tiny variations in classifier confidence.

**Loss function**

Since we use DPOTrainer instead of implementing it from scratch, we spend sometime here to understand its training objective, the loss function.

The DPO objective uses the policy and reference log-probabilities of the two continuations:

```math
\mathcal{L}_{DPO} =
-\log \sigma\left(
\beta\left[
\log\frac{\pi_\theta(y_w|x)}{\pi_{ref}(y_w|x)}
-
\log\frac{\pi_\theta(y_l|x)}{\pi_{ref}(y_l|x)}
\right]\right)
```

Here, $y_w$ is the chosen continuation and $y_l$ is the rejected continuation.

We'll use the standard sigmoid DPO loss with beta=0.1.

**Intuition behind this loss**

The core of this loss is a binary classification objective: it hopes that after the model update, the "relative score" of the chosen response $y_w$​ is higher than that of the rejected response $y_l$. Here, the "score" is not an explicit reward value, but rather the log probability ratio of the policy model relative to the reference model, $\beta \log\frac{\pi_\theta(y_w|x)}{\pi_{ref}(y_w|x)}$, which can be understood as an "implicit reward".

If the model assigns higher relative probability to the chosen response, the value inside the sigmoid parentheses is positive, the sigmoid output is close to 1, the log is close to 0, and the loss is small. Conversely, if the model instead assigns higher relative probability to the rejected response, the loss becomes large. Therefore, minimizing this loss is essentially teaching the model to increase the likelihood of the chosen response and decrease the likelihood of the rejected response, while being constrained by the reference model to prevent excessive deviation.

**Two kinds of continuation**

1. Interrupted run: detect the latest checkpoint-N and resume it, including optimizer and scheduler state.
2. Completed run: start a new training phase from the best R2 model, but retain the original R1 model as the reference. This starts a fresh optimizer and scheduler.

For the second case, we'll use a new run directory. That avoids accidentally treating an already completed checkpoint as an interrupted run.

The important behavior is:
- If Colab disconnects during training, the next execution detects the latest checkpoint and resumes.
- The model weights, optimizer state, scheduler state, and training progress are restored.
- It does not restart from `R1` and repeat the earlier training steps.

**How to resume and continue training**

This is worth understanding carefully because it will be useful in our later PPO and GRPO experiments too.

**Scenario A: Colab disconnects during training**

Simply rerun the notebook from the beginning, retaining the same:

```python
RUN_NAME = "run_01"
INITIAL_POLICY_PATH = R1_CHECKPOINT
```

The code detects the latest checkpoint-N under runs/run_01 and resumes training.

Don't delete that directory.

**Scenario B: R2 finishes, and we want to improve it further**

Suppose R2 completes three epochs, and you want to train for another two epochs.

Change the configuration to:
```python
RUN_NAME = "run_02"
# Start from the best R2 model.
INITIAL_POLICY_PATH = str(BEST_MODEL_DIR)
# Keep the reference model unchanged.
REFERENCE_MODEL_PATH = R1_CHECKPOINT
# Train for another two epochs.
NUM_TRAIN_EPOCHS = 2
```

The new run will use:
```
r2_checkpoints/
    runs/
        run_01/
        run_02/
    r2-dpo-best/
```

This is a new training phase:

- Policy starts from the best R2 model.
- Reference remains the original R1 model.
- A new optimizer and scheduler are initialized.
- New checkpoints are saved under run_02.

This is a legitimate way to continue DPO optimization without accidentally reusing an exhausted learning-rate schedule.

**Important**: Don't change RUN_NAME when recovering an interrupted run. Only change it when deliberately starting a new training phase.

### Q & A

**Can we simply use policy model without a reference model?**

Basically, this is to ask to drop the reference part in the denominator from our loss function:

```math
\mathcal{L}_{DPO} =
-\log \sigma\left(
\beta\left[
\log\frac{\pi_\theta(y_w|x)}{\pi_{ref}(y_w|x)}
-
\log\frac{\pi_\theta(y_l|x)}{\pi_{ref}(y_l|x)}
\right]\right)
```


It turns out we can indeed remove the reference model and directly use only the policy model to calculate the log probability difference between the chosen and rejected responses. This idea is feasible in theory and has corresponding methods in practice (such as SimPO, ORPO, etc.), but it will change the learning dynamics and bring a core risk: the training target becomes a "moving target," and the model may drift increasingly far from the preference data distribution.

- What happens with direct dalculation?

The form we ask for is essentially optimizing `log π(y_w|x) - log π(y_l|x)`, making it as large as possible. In actual implementations, SimPO does something similar: it directly uses the average log probability of the policy model to calculate the difference between the two responses, and adds a margin term `γ` to ensure a sufficiently large gap between the chosen and rejected responses.

This approach does eliminate the need for the reference model, saving the memory and computation of one model. The implementation is also simpler: no need to maintain a frozen copy, and no need to calculate reference log probabilities.

- Why do we still need the reference model in standard DPO?

The reference model in DPO plays a role as a "fixed anchor point." Its log probability `log π_ref(y|x)` does not change with training, so the "relative score" of each response is always compared against the same baseline. This brings several benefits:

First, it prevents the model from drifting too far. Without the reference model, the model is essentially comparing with "its past self." Early in training, when the model is weak, both the chosen and rejected responses may be poor; the loss signal is weak. Later, the model begins to prefer its own choices, and the target drifts along with the model's own improvements, potentially ending up far from the original preference data distribution.

Second, it addresses the issue of "premature satisfaction." Research points out that when the reference model itself prefers the rejected response (called a pessimistic pair), DPO's gradient will be prematurely attenuated—the policy only needs to "beat the reference model" to stop learning, even if it is still wrong. The reference model is not perfect, but it provides a stable comparison point. If we remove it entirely, this stabilizing signal disappears, and the model may converge faster in the early stage, but it is more likely to plateau later or even degrade.

Third, the KL constraint has a theoretical basis. The derivation of DPO starts from the RL objective with KL regularization, and the reference model is the anchor point for this regularization (no explicit KL term in above loss function, but it is baked into the loss structure). Removing it is equivalent to removing the KL constraint, and the optimization objective becomes "purely increasing the margin of the chosen response," with no mechanism to prevent the model from sacrificing overall language quality for the sake of margin.

- Trade-offs in practice
  
Methods without reference models (such as SimPO, ORPO) are not unreasonable. They typically add explicit regularization terms to compensate for the absence of the reference model. For example, SimPO adds a target reward margin γ to encourage the model to produce a large enough gap between chosen and rejected responses. The cost is that you need to tune this margin hyperparameter, and the training dynamics differ from DPO: faster convergence initially, but with different failure modes.

If our goal is to save memory and we are willing to accept more hyperparameter tuning and potential distribution drift risks, we can try reference-free methods. But if we want more stable training and are willing to pay the cost of one additional forward pass, the reference model is a design worth keeping.
