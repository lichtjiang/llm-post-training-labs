# Conditional Sentiment Continuation Model R3 (GRPO)

Our `R3` policy will start from `R1` ("r1-sft-best"), generate several continuations for each sentiment-conditioned prompt, score those continuations using `E1` ("E1-1_2logits"), and learn to favor higher-reward generations.

That gives us a clean comparison:
- R1 → R2: offline preference optimization using a fixed dataset.
- R1 → R3: online policy optimization using newly generated continuations and reward feedback.


## Learning Objectives

- GRPO

## Dataset

GRPO only needs prompts. It will generate its own completions.

We'll construct prompts from the SST-2 dataset using the same basic splitting approach as R1: take approximately 50–70% of a review as the prefix, and use its sentiment label as the requested sentiment.

We'll use 1,000 training prompts and 100 validation prompts for the first run.

The resulting dataset has just one column: `prompt`, for example:
```
Sentiment: positive
Continue the following review:
that loves its characters and communicates something
```

An important experimental note: `E1` ("E1-1_2logits") was trained using SST-2, so its reward signal is not an independent human evaluation. We are deliberately using it as a learned reward model to demonstrate GRPO, but we should watch for reward hacking.

## Training loop

```
        Prompt dataset
Prompts only — no chosen/rejected continuations
              ↓
R1 policy generates 4 continuations per prompt
Fresh online rollouts at each training step
              ↓
        E1 reward classifier
Scores the original review prefix + generated continuation
              ↓
    Group-relative advantages
Compare the four rewards for the same prompt
              ↓
        Update R3 policy
Increase the likelihood of higher-reward continuations
              ⟳
 Repeat with newly generated continuations
```

This is the central GRPO distinction from DPO: we do not prepare a fixed set of preferred and rejected responses beforehand. The policy generates its own candidates during training. This is exactly how online methods such as GRPO differs than offline methods such as DPO. TRL calculates group-relative advantages from their rewards and optimizes the policy out of the box.

## Understand the code

**Initial experiment settings**
```
Setting                 R3 starting value
--------------          -----------------
Initial policy          R1 SFT

Reward model            E1 SST-2 classifier

Training prompts        1,000

Validation prompts      100

Generations per prompt  4

Maximum completion      40 tokens

Epochs                  1

Learning rate           1e-6

KL coefficient (beta)   0.04

Sampling temperature    0.9

Top-p                   0.95
```

These are conservative starting settings for an educational GPT-2 experiment, not universal GRPO hyperparameters.

**Reward design** 

Initially, we use just one reward: E1's probability for the requested sentiment. This keeps the experiment easy to understand. We can later investigate reward shaping for coherence and length, but adding those now would make it harder to identify what GRPO learned.

**Load the E1 reward model**

This is the most important part of the implementation.

Our reward model is the `E1` binary sentiment classifier:

- Class 0: negative.
- Class 1: positive.
- GPT-2 backbone.
- Linear classification head: 768 → 2.
- Maximum input length: 128 tokens.
- Classification uses the hidden state of the last real token.

We should score the complete review, not just the generated continuation.

For example:

    that loves its characters and communicates something very special about humankind


We should not give `E1` the instruction `Sentiment: positive`, because that would contaminate the classifier's input.

**Implement the GRPO reward function**

This is where we connect E1 to GRPO.

TRL's custom reward function receives the generated completions and their corresponding prompts. It must return one scalar reward per completion.


Our reward function will:

1. Extract the requested sentiment from each prompt.
2. Extract the original review prefix.
3. Append the generated continuation.
4. Pass the complete review to E1.
5. Return the probability of the requested sentiment.

The reward is:
```math
R(x,y)=
\begin{cases}
P_{\text{E1}}(\text{positive}\mid x+y), & \text{if positive requested}\\
P_{\text{E1}}(\text{negative}\mid x+y), & \text{if negative requested}
\end{cases}
```

The reward values will depend on our E1 checkpoint. The important thing is that the function returns two valid floating-point numbers between 0 and 1 (alternatively, we can use a frontier LLM or Jev AI model in place of `E1` if cost is out of the equation).

**Configure and run GRPOTrainer**

A few configuration decisions are worth explaining.

```
num_generations=4
```

For each prompt, GRPO generates four candidate continuations. It compares their rewards to calculate group-relative advantages.

```
beta=0.04
```

This controls KL regularization against the reference policy. We enable it to discourage the policy from drifting too far from its initial R1 behavior. In TRL, a nonzero beta enables the reference-model KL term. 

```
loss_type="grpo"
```

We explicitly select the classic GRPO loss rather than TRL's newer DAPO default. This makes our experiment easier to connect to the original GRPO formulation. Note that classic GRPO has a known sequence-length bias; our short, 40-token completion limit keeps this first experiment relatively simple.

**Expected training steps**

With 1,000 training prompts and a per-device batch size of 4:

```math
\text{Steps per epoch}
=
\left\lceil \frac{1000}{4} \right\rceil
=250
```

We therefore expect approximately 250 optimizer steps for one epoch.

Each prompt produces four completions. That means the first run will generate approximately:

```math
1000 \times 4 = 4000
```

online continuations during training.

This is quite different from `R2`: the 4,000 continuations are generated by the evolving policy, rather than being prepared as a fixed preference dataset.

**Generation**

For the purpose of fair comparison, the function "generate_continuation" is defined and should be used for testing generation across all models in this phase (R0, R1, R2, R3, and R4).

## Things to inspect

```
Metric                              	Purpose
------                                  -------
loss                                    GRPO optimization objective

reward                                  Average combined reward

reward_std                              Reward variation across the batch

rewards/sentiment_reward_func/mean      Average E1 sentiment reward

rewards/sentiment_reward_func/std       Variation in E1 rewards

kl                                      Policy divergence from the reference

entropy                                 Diversity / uncertainty of the policy
```

The exact metric names can vary slightly with TRL versions. Refer to the current GRPOTrainer documentation on Hugging Face.

A few things to watch:

- Reward increases: encouraging, but not proof of better text.
- Reward standard deviation approaches zero: potentially a problem. If all four generations receive nearly identical rewards, GRPO has little relative learning signal.
- KL increases excessively: the policy may be drifting too far from R1.
- Entropy collapses: the policy may be producing repetitive or overly predictable continuations.

One particular failure mode to watch for is reward hacking. For example, the policy could learn to generate short, highly sentiment-loaded phrases such as "absolutely wonderful" or "utterly terrible" because E1 rewards them, even if they are poor continuations of the prefix.

That's exactly why we need to evaluate fluency and coherence independently in a real production system.

## Conceptual Comparison

The conceptual comparison is particularly important:
```
                        R2: DPO                 R3: GRPO
                        -------                 --------
Initial policy          R1                      R1

Training data           Fixed preference pairs  Prompts only

Candidate responses     Prepared beforehand     Generated online

Feedback                Chosen / rejected	Scalar reward

Reward source           Preference dataset	E1 classifier

Optimization            Direct preference	Group-relative policy 
                        optimization            optimization

Reference policy	R1                      R1
```
